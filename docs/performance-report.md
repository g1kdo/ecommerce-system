# Performance Report — Before vs. After Optimization

**Epic 4 · User Story 4.1** — query times recorded before and after indexing, with the
improvements quantified.

All numbers in this report are **measured**, not estimated. Every figure comes from a
run against a generated 1.55-million-row dataset on the machine described under
[Methodology](#methodology), and every measurement is reproducible with the commands in
[Reproducing this report](#reproducing-this-report).

## 2. Methodology

**Environment**

| | |
|---|---|
| CPU | 12th Gen Intel Core i7-1255U (10 physical / 12 logical cores) |
| RAM | 15.6 GB |
| OS | Windows 11 Pro 10.0.26200 |
| Database | PostgreSQL 18.1 (x86_64-windows), `shared_buffers` 128 MB, `work_mem` 4 MB |
| Client | PostgreSQL JDBC 42.7.13 / JDK 21 |

**Dataset** — generated by [`docs/sql/benchmark_seed.sql`](sql/benchmark_seed.sql) into a
throwaway `smart_ecommerce_benchmark` database, so the application database is never
touched:

| Table | Rows | Heap | Indexes |
|---|---:|---:|---:|
| order items | 600 000 | 30 MB | 37 MB |
| products | 200 000 | 23 MB | 40 MB |
| reviews | 300 000 | 15 MB | 21 MB |
| inventory | 200 000 | 10 MB | 8.6 MB |
| orders | 200 000 | 11 MB | 6.7 MB |
| users | 50 000 | 8.3 MB | 5.7 MB |
| categories | 20 | 8 kB | 32 kB |

Product names repeat a ten-item vocabulary (`Wireless Mouse Model 12345`, …) so text
search has realistic selectivity — roughly 1 product in 10 matches "Mouse", while a
specific model prefix matches ~11 rows.

**Measurement protocol** — for each query:

1. Drop the index under test, then `ANALYZE` so the planner is not working from stale
   statistics.
2. Run the query once to warm the cache, then **5 timed runs**; record the **median**
   of `EXPLAIN (ANALYZE)` *Execution Time*.
3. Create the index (recording build time), `ANALYZE` again.
4. Repeat the 5 timed runs and record the median.
5. Capture the top plan node in both states, because a timing change without a plan
   change is not an indexing effect.

**Caveats, stated up front**

- All measurements are **warm-cache**. On a cold cache the sequential scans would look
  considerably worse, so these ratios are the *conservative* case.
- Timings are from a laptop running other work; connection-establishment measurements
  in particular varied between 58 ms and 96 ms across runs. Query execution times were
  stable (medians of 5, spread under 10%).
- `EXPLAIN (ANALYZE)` execution time excludes network transfer of the result set to the
  client, which is why section 5's end-to-end Java numbers are larger than section 3's.

## 3. Before/after detail, per query

Plan node names are taken from the actual `EXPLAIN` output.

### Q1 — Product lookup by exact name (case-insensitive)

```sql
SELECT * FROM Products WHERE LOWER(name) = 'wireless mouse model 12345';
```

| | Before | After |
|---|---|---|
| Plan | `Gather` → parallel Seq Scan on products | `Index Scan using idx_products_name_lower` |
| Median time | 160.744 ms | **0.359 ms** |

**448× faster.** Without the functional index, PostgreSQL must compute `LOWER(name)`
for all 200 000 rows — it parallelises the scan across workers, which is why the plan
shows `Gather`. Index build: 1 922 ms, 9.7 MB.

### Q2 / Q3 — Product prefix search

```sql
SELECT * FROM Products WHERE LOWER(name) LIKE 'wireless mouse model 1234%';
```

| | No index | `idx_products_name_lower` (Q2) | `… text_pattern_ops` (Q3) |
|---|---|---|---|
| Plan | parallel Seq Scan | **still** parallel Seq Scan | `Index Scan using idx_products_name_lower_pattern` |
| Median time | 106.575 ms | 99.207 ms | **0.125 ms** |

**The index in `schema.sql` does not accelerate prefix search at all** (1.2×, which is
noise). A default B-tree is ordered by the database collation, so it cannot answer
`LIKE 'prefix%'`. An operator-class index can:

```sql
CREATE INDEX idx_products_name_lower_pattern ON Products (LOWER(name) text_pattern_ops);
```

That yields **853×**. Build: 901 ms, 9.7 MB.

### Q4 — Substring search, the query the application actually runs

`ProductDAO.searchByName` issues a leading-wildcard `LIKE`, which **no B-tree can
serve** — not even the `text_pattern_ops` variant:

```sql
SELECT * FROM Products WHERE LOWER(name) LIKE '%mouse model 1234%';
```

| | Before | After (`pg_trgm` GIN) |
|---|---|---|
| Plan | parallel Seq Scan | `Bitmap Heap Scan` + GIN index scan |
| Median time | 109.360 ms | **11.218 ms** |

**9.7× faster** using a trigram index:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_products_name_trgm ON Products USING GIN (LOWER(name) gin_trgm_ops);
```

Build: 3 096 ms, 9.2 MB — the most expensive index to build and maintain here, which is
the price of supporting arbitrary substring matching.

### Q5 — Order history for one user

```sql
SELECT * FROM Orders WHERE user_id = 12345 ORDER BY order_date DESC;
```

| | Before | After |
|---|---|---|
| Plan | `Gather Merge` → parallel Seq Scan + Sort | `Sort` → `Index Scan using idx_orders_user` |
| Median time | 71.597 ms | **0.307 ms** |

**233× faster.** Build: 537 ms, 2.4 MB. This is the "My Orders" screen.

### Q6 — Line items for one order

```sql
SELECT * FROM OrderItems WHERE order_id = 12345;
```

| | Before | After |
|---|---|---|
| Plan | `Gather` → parallel Seq Scan over 600 000 rows | `Index Scan using idx_orderitems_order` |
| Median time | 118.118 ms | **0.232 ms** |

**509× faster.** Build: 956 ms, 9.4 MB.

### Q7 — Category listing, paginated

```sql
SELECT * FROM Products WHERE category_id = 7 ORDER BY name LIMIT 20 OFFSET 0;
```

| | Before | After |
|---|---|---|
| Plan | `Limit` → Sort over 10 000 matching rows | `Limit` → cheaper Sort (index-filtered) |
| Median time | 68.450 ms | **16.766 ms** |

Only **4.1×** — the smallest real gain in the set, and the reason is the `ORDER BY
name`. The index narrows 200 000 rows to the category's 10 000, but those still have to
be sorted. A composite `(category_id, name)` index would let the sort be skipped
entirely; see the recommendations. Build: 652 ms, 1.3 MB.

### Q8 — Average rating for a product

```sql
SELECT AVG(rating) FROM Reviews WHERE product_id = 12345;
```

| | Before (index dropped) | After |
|---|---|---|
| Plan | `Index Scan using reviews_product_id_user_id_key` | `Index Scan using idx_reviews_product` |
| Median time | 0.265 ms | 0.227 ms |

**No meaningful change (1.2×), because the query was never unindexed.** See section 4.

### Q9 — Login lookup by email

```sql
SELECT * FROM Users WHERE email = 'user12345@example.com';
```

| | Before (UNIQUE constraint dropped) | After |
|---|---|---|
| Plan | `Seq Scan on users` | `Index Scan using users_email_key` |
| Median time | 8.600 ms | **0.163 ms** |

**53× faster.** The ratio is smaller than the product queries only because `users` is
the smallest of the large tables (50 000 rows). Constraint rebuild: 976 ms.

### Q10 — Order detail join

```sql
SELECT oi.order_item_id, p.name, oi.quantity, oi.unit_price
FROM OrderItems oi JOIN Products p ON p.product_id = oi.product_id
WHERE oi.order_id = 12345;
```

| | Before | After |
|---|---|---|
| Plan | `Gather` → parallel Seq Scan + Hash Join | `Nested Loop` over two Index Scans |
| Median time | 117.271 ms | **0.202 ms** |

**580× faster.** The index does not just speed up the filter — it changes the *join
strategy*. With an index the planner can nest-loop three rows against the product
primary key instead of hashing 600 000 rows.

## 4. Findings that changed our conclusions

Three results are worth more than the raw speed-ups, because they contradict what the
schema comments assume.

### 4.1 `idx_products_name_lower` does not do what its comment claims

`schema.sql` labels it "Case-insensitive product search (Epic 3 requirement)". It
serves exact-match lookups (448×) but is **useless for both search patterns the UI
offers**: prefix search needs `text_pattern_ops` (Q2 vs Q3) and the substring search
`ProductDAO` actually issues needs a trigram index (Q4). The measured gap between the
index we have and the index the query needs is **99.207 ms vs 0.125 ms**.

### 4.2 `idx_reviews_product` is redundant

`Reviews` already carries `UNIQUE (product_id, user_id)`, whose B-tree leads with
`product_id`. With `idx_reviews_product` dropped, the planner simply uses the
constraint's index:

```
Aggregate  (cost=12.39..12.40 rows=1)
  ->  Index Scan using reviews_product_id_user_id_key on reviews
        Index Cond: (product_id = 12345)
```

The extra index costs **6.2 MB** and slows every review insert/update for no read
benefit. Dropping it is a safe optimization.

### 4.3 Parallel query masks how bad the unindexed case is

Most "before" plans show `Gather` — PostgreSQL threw multiple workers at the sequential
scan. On this 12-thread laptop that hides much of the cost. On a smaller server, or
under concurrent load where workers are contended, the unindexed timings would be
materially worse. **The measured speed-ups are lower bounds.**

## 5. Application-layer optimizations

These are optimizations already present in the code, measured end-to-end through the
service layer (so they include JDBC and object mapping, unlike section 3).

### 5.1 Single query instead of N+1 — `InventoryService.getStockByProduct()`

The stock screen needs a quantity per product. Fetching them one at a time:

| Approach | Time | |
|---|---:|---|
| 200 × `getStock(productId)` | 16 427.8 ms | `████████████████████████████` |
| 1 × `getStockByProduct()` | 589.0 ms | `█` |

**27.9× faster.** Caveat worth recording: the single query loads *all* 200 000 stock
rows, so its cost is fixed regardless of page size, while the N+1 cost scales with the
page. At this dataset size the single query wins decisively; with a connection pool in
place (section 6) the crossover point would move.

### 5.2 Asynchronous logging — `LogService`

Log writes go to a daemon thread so a slow or missing document store never blocks a
checkout. Caller-thread cost for 20 events:

| Approach | Caller-thread time |
|---|---:|
| Synchronous (`Runnable::run`) | 346.2 ms |
| Daemon writer (production) | **11.3 ms** |

**30.6× less latency on the path the user is waiting on.** With MongoDB *stopped*, the
same 5 calls returned in 8 ms and printed a single warning — the user-facing action is
unaffected either way.

### 5.3 `ProductCache` — where it helps and where it does not

| Operation | Via DAO | Via warm cache | |
|---|---:|---:|---|
| 500 lookups by product id | 49 733.0 ms | **0.8 ms** | 1.53 µs per lookup |
| Substring search (11 hits of 200 000) | 118.9 ms | 33.1 ms | 3.6× |
| First call (cache warm-up) | — | 2 762.2 ms | one-off, loads 200 000 rows |

The `HashMap` is an excellent fit for its stated purpose — **O(1) lookup by id** — and
the numbers show it. But two honest qualifications:

- The warm search is a **linear scan of 200 000 entries (33.1 ms)**, which is *slower*
  than the trigram-indexed SQL query measured in Q4 (11.2 ms). At this data size,
  pushing substring search back to an indexed database would beat the in-memory scan.
- Warm-up costs 2.76 s and holds all products in heap. That is fine for a single-user
  desktop app with 200 000 products; it would not be for a larger catalogue.

## 6. The dominant cost is not a missing index

The 500-lookup figure above (49.7 s) is not really a cache result. Decomposing it:

| Component | Median |
|---|---:|
| Open + close a JDBC connection | **96.1 ms** |
| The same indexed query on an already-open connection | **0.26 ms** |
| 500 queries reusing one connection | 203.6 ms total |

**Every DAO method opens its own connection** (`try (Connection conn =
DBConnection.getConnection())`), so ~99.7% of a point lookup is connection setup. URL
tuning barely helps — it is the handshake itself, not encryption:

| Connection URL | Median |
|---|---:|
| `jdbc:postgresql://localhost:5432/…` | 72.7 ms |
| `…?sslmode=disable` | 58.4 ms |
| `…?sslmode=disable&preferQueryMode=simple` | 82.3 ms |
| `jdbc:postgresql://127.0.0.1:5432/…?sslmode=disable` | 74.2 ms |

Disabling SSL negotiation saves ~20%; a connection pool would remove essentially all of
it. **Introducing a pool is the single highest-value change available** — larger than
any individual index, because it applies to every query the application makes.

## 7. Recommendations, in priority order

| # | Change | Evidence | Expected effect |
|---|---|---|---|
| 1 | Add a connection pool (e.g. HikariCP) | §6: 96.1 ms connect vs 0.26 ms query | Removes ~96 ms from **every** DAO call |
| 2 | Add `pg_trgm` GIN index for the substring search the UI runs | Q4: 109.4 → 11.2 ms | 9.7× on the main search box |
| 3 | Add `text_pattern_ops` index if prefix search is offered | Q2 vs Q3: 99.2 → 0.125 ms | 853× on prefix search |
| 4 | Make the category listing index composite `(category_id, name)` | Q7: only 4.1×, sort still dominates | Removes the sort step |
| 5 | Drop the redundant `idx_reviews_product` | §4.2: constraint index already serves it | Frees 6.2 MB, faster review writes |
| 6 | Keep every index in `schema.sql` that was measured here | Q1, Q5, Q6, Q9, Q10: 53×–580× | Already earned |

Index maintenance is not free — total index footprint on this dataset is ~62 MB against
~98 MB of table data, and each index adds write cost. Recommendations 2 and 3 overlap:
if only substring search is exposed in the UI, the trigram index alone is enough.

## 8. Reproducing this report

```bash
createdb -U postgres smart_ecommerce_benchmark
```

```bash
psql -U postgres -d smart_ecommerce_benchmark -f docs/sql/schema.sql
```

```bash
psql -U postgres -d smart_ecommerce_benchmark -f docs/sql/benchmark_seed.sql
```

Then, for any query, measure both states in one session:

```sql
DROP INDEX IF EXISTS idx_orders_user;
ANALYZE;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM Orders WHERE user_id = 12345 ORDER BY order_date DESC;
CREATE INDEX idx_orders_user ON Orders (user_id);
ANALYZE;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM Orders WHERE user_id = 12345 ORDER BY order_date DESC;
```

Take the median of five runs after one warm-up, and confirm the top plan node changed —
a timing difference without a plan change is measurement noise, not an index effect.

Drop the throwaway database when finished:

```bash
dropdb -U postgres smart_ecommerce_benchmark
```
